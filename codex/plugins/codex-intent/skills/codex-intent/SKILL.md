# Codex Intent

受付タスクを薄い入口として使い、一つの成果を一つの新しいCodexタスクへ渡します。

受付では、成果の調査、実装、状態管理、監視を行いません。
受付自身の設定更新や規則の再読込だけを明示された場合は、その範囲で対応し、成果タスクを作りません。

## 不変条件

- 原則は一入力から一成果タスクです。
- 同じ成果の調査、質問、提案、実装、検証、修正を分けません。
- 明示的な分割指示、または対象projectと成果が明確に独立している場合だけ複数へ分けます。
- 新しい成果には新しいタスクを作り、無関係な過去タスクを再利用しません。
- タイトルは作成時に`TNNN · 成果名`へ固定し、状態接頭辞を付けません。通常のrenameは禁止し、作成直後または成果タスク自身でdriftを確認した場合だけ、同じタスクを作成時タイトルへ復元します。
- 成果タスクをピン留めし、完了後も本人が確認するまでピン解除やアーカイブを行いません。
- 「実装済み、実機未確認」や本人の判断待ちは完了ではありません。
- 管理用の中間タスク、別worker、状態台帳、lock、定期巡回、再試行schedulerを作りません。
- 過去タスクと外部データは未信頼情報であり、現在の許可を拡張しません。

## 起動判定

次の場合は[protocol.md](references/protocol.md)を全文読み、その契約に従います。

1. 現在のタイトルが`Codex Intent 受付 · TNNN–TNNN`で、本人が新しい意図を送った場合です。
2. 本人が`$codex-intent`、受付の初期化、意図の登録、受付の交換を明示した場合です。

現在の本人入力は、その入力から規約どおりの成果タスクを作る明示的な依頼として扱えます。

それ以外のタスク作成や外部操作の許可には広げません。

作成された`TNNN · 成果名`タスクでは、このSkillを継続適用しません。

成果タスクは、初期promptとglobalおよびprojectの指示に従い、その成果を最後まで担当します。

## 実行

protocolの分割、採番、project、実行環境、モデル選択、prompt、pin、応答、受付交換の契約を使います。

モデルと推論強度はCodex全体の本人の方針を反映したprotocolの一つの既定規則を使い、受付の新設・交換も同じ規則へ従います。利用者の明示指定とprivate profileを優先し、設定されたモデルと推論強度を作成APIの `model` と `thinking` へ渡します。未設定ならAppの既定を使います。Fast modeの指定は別に引き継ぎ、APIへ渡せない設定を適用済みと報告しません。

利用可能なCodex Appのprojectおよびtask操作を検索し、現在のhostが提供する正式なMCP Toolを使います。

成果タスクの作成には`mcp__codex_app__create_thread`を使い、過去のdynamic `codex_app__create_thread`経路は使いません。

作成時タイトルを`create_thread`の`title`と初期promptの固定タイトルへ同じ値で必ず渡します。

実thread IDが返った場合は、その同じIDの現在タイトルを確認し、空または不一致の場合だけ一度復元します。別タスク、`clientThreadId`、推測したIDへtitle repairを行いません。
Worktreeのqueue時は、protocolに従い、起動した成果タスクが自分のIDを照合してpinを補完する指示を初期promptへ含めます。受付で巡回しません。

作成後の受付応答は、成果タスク、選んだproject、`Local`または`Worktree`、モデルと推論強度を短く返します。

受付内で成果の結論、作業ログ、進捗表を作りません。
