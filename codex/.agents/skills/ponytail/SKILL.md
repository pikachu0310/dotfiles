# Ponytail：必要な品質を少ないコードで仕上げる

依頼の成果を全部満たす、分かりやすい実装を選ぶ。小さな差分は判断基準の一つであり、体験・見た目・音・アクセシビリティ・作者の素材や演出を削る理由にしない。本人が磨き込みを求めた場面では、その品質まで完成させる。

## 実装の選び方

- 現在のコードと利用経路を読み、呼出元・設定・保存データ・公開APIへの影響をつかむ。旧generatorやbuilderを再実行して、本人が手直しした原本や現在の完成成果を戻さない。依頼に必要な範囲を最後まで扱い、無関係な機能や将来用の設定は増やさない。
- 既存の関数・コンポーネント・サービス・素材を先に探す。次に標準機能、導入済みの依存、必要な小さな実装を比較する。project固有の部品・構造を尊重し、既存の依存を使えるだけで目的に合わないものまで採用しない。
- 抽象化・wrapper・新しい依存・柔軟な設定は、今の成果に必要な場合だけ加える。短くても読みにくい一行より、意図が明確なコードを選ぶ。
- 不具合は症状の箇所だけで済ませず、呼出元を探し、守るべき状態とその所有者を確かめて原因を直す。断定できなければ、原因候補を絞る観察を一つ選ぶ。
- 移動・共通化で、入力検査・error handling・保存の保護を落とさない。既知の制約は、保守に役立つ場所へ理由と適用範囲を短く残す。
- 必要な機能追加は、依頼・ゲームデザイン・現在の体験から価値を説明できるものにする。必要性が明らかな改善は自走し、選択で成果が変わる場合だけ本人に聞く。

## 本人の運用に合わせる

実装をまとまって進める。小変更ごとのテスト・QA、各修正へのassert追加、常時reviewやauditは要求しない。必要な確認は成果の区切りでごく稀にまとめ、生成・ビルド・見た目や体験の観察は目的に合わせて行う。未確認を成功扱いにしない。

このskillは適用した仕事の実装判断に使う。会話全体に固定のmodeや質問工程を持ち込まず、既に合意した実装を再承認待ちにしない。報告には成果と、判断に必要な未確認事項を示し、定型の注意書きを毎回足さない。
