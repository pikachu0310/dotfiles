# VRChatワールド制作

## 体験から作る

- 最新の本人レビューと現在の成果から続ける。品質を保って完成まで自走する。機能追加はゲームデザイン上の必要性で判断し、過剰設計や無駄な機能を増やさない。
- 対象プラットフォームと既存のUnity・SDK・描画構成に合わせる。実行時はUdonSharp・対応APIを使い、Editor用生成コードと分ける。
- 既存の素材・完成体験を最大限使い、作者のモデル・モーション・演出・判定を簡易版へ置き換えない。不足時は外部も広く探し、用途・品質・VRChat対応・利用条件から候補を絞る。見つからない素材や本人の選定が必要なものは、用途・不足・候補を最終返信に短く示して依頼し、独立した制作を続ける。
- 分かりやすい体験から作り、細かなルール・設定は興味のある人が詳細を開ける形にする。表せるものはアイコンにし、言葉が不可欠な箇所だけ短く添える。AIらしい飾り文句を除く。
- 関連情報と操作を近くに集め、視界を塞がずVRでも押しやすくする。主役の体験に空間を合わせ、不要な移動・装飾・物量を減らす。
- 既定値で最も良い体験を作る。調整機能は必要な場合だけ。操作は分かりやすくし、難易度・駆け引き・企画の狙いを保つ。
- キャラの開始・移動・接触・終了を自然につなぎ、過剰な演出で主役を隠さない。NavMesh等で移動するNPCはIn PlaceとRoot Motion設定を制御方式に合わせ、二重移動・足滑りを避ける。音も基本品質に含め、既存SEを比較し、用途・タイミング・音量を整える。
- 日英を基本に、タイムゾーンから初期言語を自動選択し、言語切替ボタンを常に用意する。
- 複数人では個人表示と共有状態を分ける。NavMesh移動は目的地と必要な行動状態を共有し、各端末で滑らかに動かす。連続した位置同期でガクつかせない。途中参加・所有者変更でも同期済み状態から復元する。
- 実装をまとめて進め、必要な生成・ビルド・見た目確認を行う。レビューを求める点は毎回短く、答えやすい形にする。ClientSim・実VR・複数人で確認した範囲を区別し、未確認を成功扱いにしない。

## デザインを実装まで仕上げる

- 画像生成・編集は、公式資料で最新の用途に合うモデルを確認し、正式なブラウザツールから通常のChatGPT（Classic/Chat）の本人が利用を許可したアカウントへ、依頼のpromptと指定参照だけを送る。利用可能なら画像生成のthinkingを選び、選択状態と結果を確認する。
- 画像から配色・形・質感の狙いを具体化し、モダンで目的に合うUIを操作できる状態に仕上げる。新しい立体物はBlenderで作り、実物資料と用途から寸法・構造を決める。ラフで視線・動線と、座る・手を伸ばす等の使用空間を先に整える。
- 代表モデルを基準に、基本図形の配置だけで済ませず形・質感を仕上げる。支持・接合・可動軸・法線を整え、意図しない浮き・干渉を直す。同じ部品はインスタンス／Prefab、材質は共有し、UVの実寸密度・模様の向き・印字の比率を揃える。
- テクスチャはタイル材・UVアトラス・デカールの用途を分け、使用シェーダーのマップ・チャンネル・色空間に合わせる。質感の足りない箇所は既存素材も比較する。
- 本人が手直しした最新原本を保ち、原本と使った生成スクリプトを残す。修正は両方へ反映し、古いスクリプトの再生成で本人の修正を消さない。FBXでUnityへ渡し、実寸・向き・階層・材質を合わせる。
- 静的な照明はベイクを基本に、環境光・Light Probe・Reflection Probeと対応シェーダーで背景と動くキャラの見え方を整える。まとまった段階でUnityの全景と接写を見て、陰影・質感・主役の読み取りやすさを仕上げる。見た目が定まらなければ必要な候補を比較し、自分で改善案を選ぶ。
- ChatGPTが利用不能なら素材調査・実装準備を進め、利用可能になったら生成へ戻る。古いCodex内蔵imagegenや有料APIへ無断で代替しない。

## 無駄な毎フレーム処理を減らす

文字の生成・更新を毎フレーム行わない。値の変化時か必要な低頻度で更新する。参照を再利用し、単純な反復動作は既存Animator等を活用する。即座にreturnする軽い処理より、不要な間も走る重い処理を優先する。滑らかな追従・作者演出・再開動作を保つ。

制作中に確認した具体例：

- 文字・UI：動画の時刻・音量の文字生成を変化時にし、調整UIを定期イベントへ。同じ案内文・ハイライトの再更新を省く。
- キャラ：視線・骨・表情が自然に戻り切った後、誘導NPCの移動・旋回が完了した後だけ休止し、対象や操作の変化で再開する。
- 映像・音：未使用TVGIの画像コピー・GPU読出しを撤去し、停止中AudioLinkのサンプル取得・配列コピー／送信を省く。余韻と必要な時刻更新は保つ。

## 通常確認と復旧で止まらない

依頼で許可された編集・保存・ビルド・通常復旧は、同じ許可を聞き直さず進める。ClientSimのAccept、SDKの著作権確認・投稿・アップロード等は、その利用者が対象と内容を許可した範囲だけ扱う。新しい環境に制作者の過去の許可を引き継がない。現在の調査のみ等の指定は守る。

- 保存・ビルド中は少し待ち、進行があれば待機を続ける。一度のtimeoutで故障扱いせず、終了後に再取得する。
- クリックが反映されない時は、本人の別作業による画面・フォーカス変更も考慮し、少し待って対象を取り直す。前面化・重なるパネルの移動後、現在の画面で押して離す。Accept完了後にゲーム確認を始める。
- 接続不良は所有projectPath・PID・listener・instanceIdから現在のportを取り直し、Stoppedなら通常toggleで再開する。
- 主画面がなければ所有チャットがSceneとSDK進行を保ち、通常終了後、同projectをREADME記載の `scripts/start-unity-visible.ps1` でNormal起動する。
- `failed to write kernel assets … (os error 3)` は、native Windows PythonでREADME記載の `scripts/repair-windows-node-repl-assets.py --repair` を実行し、欠損した一時保存先を復元する。その後、正式ツールを再初期化し、一覧・対象画面を取り直して再開する。`js_reset`だけで済ませず、GPU不調と決めつけない。
- `os error 267` はcwdの実在と用途を確認し、欠損directoryを復元できれば復元して、同じチャットで正式ツールを再接続する。同じ障害が続けば原因を切り分け、無関係な入力を繰り返さず独立作業を続ける。

Windows操作は現行公式skillと共有leaseを使い、待機中は解放する。ツール自身の安全停止・アクセス制御と本人の操作停止は回避しない。復旧scriptの所在・手順は[READMEのComputer Use guidance](../../../../README.md#computer-use)を必要時に読む。
